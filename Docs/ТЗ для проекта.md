# Техническое задание: платформа сбора и анализа данных по торгам доменов

### Задачи
- формально описать схему `observation message` в виде окончательного контракта;
- формально описать границы ответственности парсера и приемника;
- утвердить внутренний справочник статусов торгов и правила маппинга статусов площадок;
- утвердить правило определения финального статуса при исчезновении лота;
- утвердить минимальный обязательный набор полей по лоту для MVP;
- утвердить стратегию дедупликации observation-сообщений;
- утвердить формат хранения `RawPayload` и расширяемых атрибутов;
- определить финальный набор endpoint’ов API для первой версии.

### Возможно (подумать)
- описать формат конфигураций парсеров;
- описать правила логирования и уровни ошибок;
- описать правила retry для RabbitMQ consumer и для самих парсеров;
- описать стратегию dead-letter обработки;
- описать правила эволюции схемы observation-сообщений по `SchemaVersion`.

---

## 1. Назначение системы

Разработать платформу, которая автоматически собирает, нормализует, хранит и предоставляет через API данные о доменах, выставленных на аукционных площадках продажи доменов.

Система должна собирать информацию:
- на каких площадках выставлялся домен;
- в каких торгах участвовал домен;
- по какой цене домен выставлялся;
- какова была финальная цена домена;
- был ли домен продан или не продан;
- когда завершились торги;
- какие ключевые наблюдения по лоту были зафиксированы в процессе торгов.

Собранные данные в дальнейшем будут использоваться для:
- анализа рыночной стоимости доменов;
- оценки интереса к доменам;
- построения исторических отчетов и аналитики;
- отслеживания повторных продаж одного и того же домена;
- последующего принятия решений о покупке доменов.

## 2. Цели проекта

### 2.1 Бизнес-цели
- Получить единое хранилище данных по доменным аукционам из нескольких источников.
- Минимизировать потери данных по закрывающимся торгам.
- Обеспечить возможность последующего анализа цен, спроса и динамики по доменам.
- Обеспечить быстрое подключение новых источников без переработки модели хранения.

### 2.2 Технические цели
- Построить изолируемую систему независимых парсеров.
- Разделить сбор данных и бизнес-логику сохранения.
- Реализовать приемник, который централизованно обрабатывает наблюдения от парсеров.
- Реализовать API для получения доменов, торгов, финальных цен и истории.
- Инкапсулировать всю работу с БД в сервисном слое на .NET + EF Core + PostgreSQL.

## 3. Границы системы

### 3.1 Что входит в систему в текущем MVP
- независимые программы-парсеры по площадкам;
- очередь сообщений между парсерами и приемником;
- программа-приемник, обрабатывающая observation-сообщения;
- сервисный слой записи в БД;
- хранилище доменов, торгов, финальных цен и истории наблюдений;
- API для чтения данных;
- логирование ошибок, событий приема и обработки.

### 3.2 Что не входит в MVP
- отдельный централизованный scheduler как самостоятельный системный компонент;
- отдельная централизованная система управления задачами парсеров;
- UI-админка;
- сложная ролевая модель;
- публичная auth/JWT;
- сложная аналитика и ML-модели оценки стоимости;
- полная история всех ставок по каждому лоту;
- автоматизированный универсальный обход CAPTCHA.

### 3.3 Что допускается в MVP как упрощение
- логика планирования работы парсера находится внутри самого парсера;
- retry-политика находится внутри самого парсера;
- конфигурации парсера, cookies, headers, сессии и технические настройки могут храниться локально в конфигурации конкретного парсера;
- приемник реализуется как монолит бизнес-логики с логическим разделением на внутренние модули.

## 4. Основные сценарии использования

### 4.1 Сбор данных по активным торгам
Парсер площадки получает список активных торгов, извлекает из них данные и отправляет в очередь observation-сообщения.

### 4.2 Учащенный сбор перед завершением торгов
Основной приоритет системы — не упустить финальный статус и финальную цену продажи. Частота опроса в MVP задается логикой конкретного парсера.

### 4.3 Учет механики продления торгов (переторжка)
Если в последние 5 минут поступает новая ставка, торги продлеваются еще на 5 минут. Парсер обязан учитывать эту механику и продолжать наблюдение до фактического завершения торгов.

### 4.4 Фиксация финального состояния до исчезновения лота
Так как после завершения торгов история часто становится недоступна, парсер должен успеть передать в очередь последнее подтвержденное наблюдение по лоту до его исчезновения.

### 4.5 Работа с несколькими площадками для одного домена
Один и тот же домен может одновременно присутствовать на нескольких площадках. При этом продажи и торги на каждой площадке рассматриваются как отдельные события.

### 4.6 Повторные продажи одного и того же домена
Если домен повторно выставляется и продается позже, даже на той же площадке, это должно сохраняться как новое отдельное событие торгов, связанное с той же сущностью домена.

### 4.7 Прием и сохранение наблюдений
Приемник читает observation-сообщения из очереди, валидирует их, нормализует, сопоставляет домен и торги, а затем решает, что создать, обновить и какую историю сохранить.

## 5. Архитектурная концепция

В текущем MVP система строится как двухуровневая архитектура:

**уровень 1: парсеры → очередь**  
**уровень 2: приемник → бизнес-обработка → БД → API**

### 5.1 Ключевые принципы
- Парсеры не работают напрямую с БД.
- Парсеры не знают структуру БД и внутренние сервисы приложения.
- Парсеры отправляют не доменные сущности, а observation-события по лотам/торгам.
- Приемник централизует бизнес-логику сохранения данных.
- Все обращения к БД выполняются только через сервисы и интерфейсы.
- Сбой одного парсера не должен останавливать систему в целом.
- Сообщения из очереди могут приходить повторно, поэтому приемник должен быть идемпотентным.
- Обработка должна опираться на время фактического наблюдения `ObservedAt`, а не только на время получения сообщения.

### 5.2 Логическая структура MVP
- **Parser Programs** — отдельные программы под каждую площадку.
- **Queue** — транспорт между парсерами и приемником.
- **Receiver** — прием и обработка observation-сообщений.
- **Domain/Application Services** — нормализация, сопоставление, сохранение.
- **Infrastructure** — EF Core, PostgreSQL, интеграция с очередью, логирование.
- **Web API** — чтение данных из системы.

### 5.3 Принятая архитектурная стратегия
Для MVP логика работы, частота опроса, retry и технические настройки находятся внутри конкретного парсера. Приемник реализуется как монолит бизнес-логики, но внутри должен быть логически разделен на отдельные модули.

## 6. Предлагаемые модули системы

### 6.1 Парсер площадки
Функции:
- сбор списка активных торгов;
- сбор деталей по лотам;
- учет логики завершения и продления торгов;
- собственная retry-политика;
- собственная логика частоты опроса;
- работа через HTTP, proxy, headless browser, JS rendering или иные механизмы при необходимости;
- формирование observation-сообщений;
- отправка observation-сообщений в очередь.

### 6.2 Очередь сообщений
Функции:
- асинхронная передача observation-сообщений от парсеров к приемнику;
- буферизация;
- развязка между скоростью парсинга и скоростью обработки.

Выбранное решение для MVP:
- в качестве очереди сообщений использовать **RabbitMQ**;
- RabbitMQ является основным транспортом между парсерами и приемником;
- очередь должна поддерживать надежную доставку observation-сообщений;
- на стороне приемника использовать подтверждение обработки сообщений;
- на стороне парсеров использовать подтверждение успешной публикации сообщений;
- архитектура очереди должна допускать повторную доставку сообщений без нарушения целостности данных, так как приемник обязан быть идемпотентным.

### 6.3 Приемник
Функции:
- чтение сообщений из очереди;
- валидация схемы сообщения;
- дедупликация;
- нормализация доменных и торговых данных;
- сопоставление с существующими сущностями;
- обновление текущего состояния;
- запись истории наблюдений, цен и статусов;
- логирование ошибок обработки.

### 6.4 Внутренние модули приемника
Внутри приемника логически должны быть выделены:
- consumer сообщений;
- validator сообщений;
- normalizer;
- matcher доменов и торгов;
- persistence layer;
- audit/logging.

### 6.5 API
Функции:
- получение списка доменов;
- получение карточки домена;
- получение истории наблюдений и цен по домену;
- получение списка торгов;
- получение карточки торгов;
- получение финальных результатов;
- получение информации по площадкам;
- получение логов и статусов обработки при необходимости.

## 7. Парсеры: требования и принципы

Каждый парсер — это отдельная программа или изолируемый модуль под конкретную площадку.

### 7.1 Общие требования к парсерам
Парсер должен уметь:
- получать список активных торгов;
- получать детальную информацию по конкретному лоту;
- определять домен, статус, цену, ожидаемое завершение торгов и финальное состояние;
- учитывать продление торгов;
- поддерживать работу с HTML-парсингом;
- при необходимости поддерживать headless browser и JS-rendering;
- поддерживать прокси, cookies, session tokens и ручную передачу данных авторизации;
- корректно обрабатывать ошибки, таймауты, рейт-лимиты и антибот-защиту;
- отправлять observation-сообщения в очередь.

### 7.2 Особенности реализации парсеров
- В первой версии основным способом интеграции является HTML-парсинг.
- У площадок может отсутствовать публичный API.
- Для отдельных площадок может потребоваться JS-rendering и headless browser.
- Авторизация может быть нестабильной из-за CAPTCHA и антибот-защиты.
- На первом этапе допускается ручная передача cookies, headers, session tokens и других данных доступа через конфигурацию парсера.
- Логика планирования, частоты запросов и retry на этапе MVP находится внутри конкретного парсера.

### 7.3 Что парсер НЕ должен делать
Парсер не должен:
- напрямую записывать домены, торги и историю в БД;
- знать внутреннюю схему БД;
- содержать бизнес-логику сопоставления сущностей системы;
- решать, какие записи окончательно создавать или обновлять в модели хранения.

## 8. Контракт observation-сообщения

Парсеры должны отправлять в очередь не “готовые домены”, а observation-события по лотам/торгам.

### 8.1 Назначение observation-сообщения
Observation-сообщение описывает факт того, что парсер в конкретный момент времени увидел на конкретной площадке определенное состояние лота.

### 8.2 Минимальный состав observation-сообщения
Рекомендуемые поля:
- `MessageId`
- `SchemaVersion`
- `ParserCode`
- `ParserVersion`
- `SourcePlatformCode`
- `ObservedAt`
- `ExternalAuctionId`
- `ExternalDomainId` (nullable)
- `DomainNameOriginal`
- `DomainNameNormalized` или сырье для нормализации
- `AuctionStatusRaw`
- `AuctionStatusNormalized` (опционально)
- `CurrentPrice` (nullable)
- `FinalPrice` (nullable)
- `CurrencyCode` (nullable)
- `AuctionStartAt` (nullable)
- `AuctionEndAt` (nullable)
- `AuctionExtendedEndAt` (nullable)
- `IsExtended` (nullable)
- `LotUrl` (nullable)
- `AttributesJson` (raw/extra fields)
- `RawPayload` или ссылка на raw payload при необходимости

### 8.3 Требования к observation-сообщениям
- сообщения должны быть версионируемыми;
- сообщения должны содержать время фактического наблюдения;
- сообщения могут приходить повторно;
- сообщения могут приходить не в исходном порядке;
- приемник должен уметь безопасно обрабатывать такие ситуации.

### 8.4 Требования к доставке сообщений через RabbitMQ
- observation-сообщения должны публиковаться в RabbitMQ;
- на стороне producer-парсера должна использоваться модель подтверждения публикации;
- на стороне приемника должна использоваться модель подтверждения обработки сообщения;
- повторная доставка сообщения считается допустимым сценарием;
- система проектируется под модель `at-least-once delivery`, а не под предположение о ровно однократной доставке;
- защита от дублей обеспечивается на стороне приемника.

## 9. Приемник: бизнес-логика обработки

### 9.1 Общая схема обработки
1. Получить observation-сообщение из очереди.
2. Провалидировать схему и обязательные поля.
3. Проверить дедупликацию и идемпотентность.
4. Нормализовать домен, валюту, время и статус.
5. Найти или создать домен.
6. Найти или создать торги по связке площадка + внешний ID торгов.
7. Обновить текущее состояние торгов.
8. Записать историю наблюдений, цены и статусов.
9. При необходимости зафиксировать финальный статус и финальную цену.
10. Сохранить результат обработки и логи.

### 9.2 Что должен делать приемник
- централизовать бизнес-логику записи в БД;
- сопоставлять один и тот же домен между разными площадками;
- разделять сущность домена и конкретное событие торгов;
- хранить последовательность торговых событий;
- определять, что надо создать, а что обновить;
- обрабатывать повторные и несортированные сообщения.

### 9.3 Что особенно важно для приемника
- идемпотентность;
- устойчивость к дублям;
- корректная обработка более старых сообщений, пришедших позже;
- приоритет финального статуса над более ранними промежуточными статусами;
- модульность внутренней реализации, несмотря на монолитную форму сервиса.

## 10. Требования к данным и хранению

### 10.1 Общие требования к хранению
Система должна обеспечивать возможность ответить на вопросы:
- когда и где домен был выставлен;
- был ли он продан или не продан;
- по какой финальной цене он был продан;
- был ли лот завершен без ставок или с нулевой финальной стоимостью;
- на какой площадке и в каких торгах участвовал домен;
- какой парсер и когда увидел соответствующее состояние.

### 10.2 Принцип хранения истории
История должна быть ориентирована в первую очередь на последовательность торговых событий и наблюдений, а не на полную историю каждой отдельной ставки.

Необходимо гарантированно хранить:
- факт выставления домена на торги;
- факт участия домена в конкретном аукционе;
- финальный статус торгов;
- финальную цену;
- признак того, что домен не был продан;
- ключевые observation-наблюдения, если они были получены.

### 10.3 Важное требование по доменным именам
Система обязана корректно работать с международными доменами (IDN):
- кириллица: `марка.рф`
- латиница: `example.com`
- смешанные и иероглифические домены: `市值管理.com`

Нужно хранить:
- оригинальное представление домена;
- нормализованное представление;
- punycode-представление при необходимости;
- TLD;
- SLD;
- язык/скрипт при возможности определения.

### 10.4 Расширяемые атрибуты
Так как площадки могут отдавать разные дополнительные поля по доменам и лотам, необходимо предусмотреть JSONB-поля в PostgreSQL для расширяемых атрибутов.

## 11. Сущности БД

Ниже приведен минимальный рекомендуемый состав сущностей для текущей архитектуры MVP.

### 11.1 Domain
Хранит уникальную сущность домена.

### 11.2 SourcePlatform
Справочник площадок.

Торги на площадке. Один и тот же домен может участвовать в нескольких независимых торгах, в том числе повторно и на разных площадках.

### 11.7 AuctionStatusHistory
История изменения статуса торгов.

### 11.8 ReceiverProcessingLog
Лог обработки сообщений приемником.

### 11.9 ParserLog
Логи парсеров.

### 11.10 SystemErrorLog
Системные ошибки. Возможно не в БД, а логом в ТГ.

## 12. Требования к БД и доступу к данным

### 12.1 Общие требования
- PostgreSQL как основная БД. Возможен в последующем переход на clickhouse. (или будем комбинировать)
- Доступ к БД только через сервисы, интерфейсы и EF Core.
- Запрещены прямые SQL-запросы из контроллеров, парсеров и приемника, кроме строго обоснованных инфраструктурных случаев.
- Логика доступа к данным должна быть инкапсулирована.
- Использовать миграции EF Core.

### 12.2 Индексация
Обязательны индексы по:
- `Domain.NameNormalized`
- `Domain.NamePunycode`
- `Auction.ExternalAuctionId + SourcePlatformId`
- `Auction.EndAt`
- `Auction.Status`
- `AuctionObservation.MessageId`
- `AuctionObservation.ObservedAt`
- `DomainPriceHistory.DomainId + ObservedAt`

### 12.3 Ограничения целостности
- уникальность домена в нормализованной форме;
- уникальность внешнего ID торгов в рамках площадки;
- уникальность `MessageId` observation-сообщения;
- исторические записи не должны теряться при обновлении текущих сущностей.

## 13. API: функциональные требования

### 13.1 API для чтения данных (Не в приоритете, MVP можно без этого)
Нужны endpoint’ы для:
- списка доменов с фильтрацией;
- карточки домена;
- истории наблюдений и цен домена;
- списка торгов;
- карточки торгов;
- списка площадок;
- финальных результатов торгов;
- технических логов обработки при необходимости.

## 14. Логика сбора по аукционам

### 14.1 Общий алгоритм на стороне парсера
1. Получить список активных торгов с площадки.
2. Извлечь домены, статус, цену, идентификатор лота и время завершения.
3. Если торги приближаются к завершению — участить опрос по внутренним правилам парсера.
4. Если обнаружено продление торгов — обновить ожидаемое время завершения и продолжить мониторинг.
5. Передать в очередь observation-сообщения.
6. До исчезновения лота попытаться передать финальное подтвержденное наблюдение.

### 14.2 Правила фиксации цены
Важно только получение финальной цены, а не хранение полной истории ставок.

Система должна:
- сохранять ключевые наблюдения цены, если они получены;
- делать обновления цены в лоте и записывать последнюю как финальную;
- фиксировать финальное наблюдение непосредственно перед завершением или исчезновением лота;
- учитывать, что часть лотов может завершаться без ставок (считаем финальную стоимость 0 тогда).

### 14.3 Правила определения финального состояния
Фактом продажи может считаться:
- исчезновение лота с площадки;
- изменение статуса лота на sold/completed/closed или аналогичный статус площадки;
- достижение финального состояния по правилам конкретного источника.

Если домен был выставлен, но не продан, это также должно фиксироваться как завершенное торговое событие с соответствующим статусом.

### 14.4 Особенности площадок без истории торгов
Если после завершения торгов площадка не предоставляет историю и финальные данные, система обязана зафиксировать результат в момент торгов. Архивное восстановление результата после завершения в первой версии не считается обязательным сценарием.

## 16. Авторизация и безопасность

### 16.1 Для API
В первой версии сложная ролевая модель не требуется. Достаточно внутреннего API без обязательной поддержки JWT.

### 16.2 Для хранения чувствительных данных
- на первом этапе допускается хранение секретов и параметров доступа в конфигурациях проекта или конфигурациях конкретных парсеров;
- чувствительные данные не должны попадать в открытые логи;
- архитектурно желательно предусмотреть возможность дальнейшего выноса секретов в отдельное хранилище.

---

## 17. Надежность и отказоустойчивость

### 17.1 Общие требования
- отказ одного парсера не влияет на работу остальных;
- приемник не должен зависеть от логики конкретного парсера;
- повторная доставка сообщения из очереди должна быть допустима;
- приемник должен быть идемпотентным;
- должна быть возможность безопасной повторной обработки сообщения.

### 17.2 Требования к конкурентности
- поддержка нескольких парсеров одновременно;
- поддержка повторной доставки сообщений;
- корректная обработка дублей;
- корректная обработка более старых сообщений, пришедших позже;
- идемпотентность сохранения данных.

### 17.3 Требования к деградации
При недоступности внешней площадки система должна:
- не падать целиком;
- фиксировать ошибку;
- выполнять локальные retry на стороне парсера;
- сохранять диагностику для последующего анализа.

---

## 18. Логирование и мониторинг

### 18.1 Что логировать
- запуск и завершение циклов работы парсеров;
- количество отправленных observation-сообщений;
- ошибки HTTP;
- ошибки парсинга разметки;
- ошибки сериализации и отправки в очередь;
- ошибки валидации сообщения на стороне приемника;
- ошибки нормализации и сохранения в БД;
- системные ошибки;
- ошибки публикации в RabbitMQ;
- случаи повторной доставки сообщений;
- случаи отказа обработки и повторного чтения сообщения.

### 18.2 Что желательно отслеживать (Опционально для MVP)
- количество observation-сообщений по площадкам;
- процент успешной обработки сообщений;
- количество дублей;
- количество ошибок по площадкам;
- lag между `ObservedAt` и временем записи в БД;
- количество завершенных торгов с зафиксированной финальной ценой;
- количество сообщений в очереди RabbitMQ;
- количество сообщений в retry/dead-letter потоках, если они будут добавлены.

## 19. Нефункциональные требования

### 19.1 Производительность
- система должна выдерживать одновременную работу нескольких парсеров;
- API должно поддерживать пагинацию и фильтрацию; (Опционально для MVP)
- приемник не должен блокировать общую обработку при единичных ошибках сообщений.

### 19.2 Масштабируемость (Не будет в MVP, но с заделом)
- возможность добавлять новые парсеры без изменения модели хранения;
- возможность заменить внутреннюю логику парсеров без изменения приемника;
- возможность в будущем вынести логику планирования задач из парсеров в отдельный orchestration-слой;
- возможность выносить тяжелые парсеры в отдельные процессы или контейнеры.

### 19.3 Поддерживаемость
- код должен быть разделен по слоям;
- каждый модуль должен иметь четкую ответственность;
- приемник должен быть логически разделен на подмодули;
- конфигурации должны быть документированы.

### 20.1 Выбранная очередь сообщений
Для MVP в качестве очереди сообщений используется **RabbitMQ**.

RabbitMQ нужен для:
- передачи observation-сообщений от парсеров к приемнику;
- буферизации нагрузки;
- надежной доставки сообщений;
- повторной доставки сообщений при ошибках обработки;
- дальнейшего расширения схемы очередей без переработки общей архитектуры.

Для MVP рекомендуется использовать:
- durable queue;
- manual ack на стороне приемника;
- publisher confirms на стороне парсеров;
- готовность к добавлению dead-letter очереди на следующем этапе;
- конфигурацию, допускающую at-least-once delivery.

## 21. Минимальный MVP

В первую версию рекомендуется включить:
- 1 стартовый парсер NickSell;
- основную интеграцию через HTML-парсинг;
- поддержку headless browser как опционального режима реализации конкретного парсера;
- архитектуру `парсеры → RabbitMQ → приемник`;
- observation-сообщения как основной контракт передачи данных;
- приемник как монолит бизнес-логики с внутренним логическим разделением;
- хранение доменов, торгов, observation-истории, цен, статусов, логов и ошибок;
- поддержку прокси, cookies и ручной передачи параметров авторизации;
- поддержку IDN-доменов;
- API для чтения доменов, торгов и финальных результатов;
- запуск в Docker на Linux.

В MVP не требуется (На будущее):
- отдельный централизованный scheduler;
- отдельная централизованная система parser tasks;
- UI-админка;
- сложная ролевая модель;
- обязательная интеграция через JWT;
- аналитический слой и ML;
- хранение полной истории всех ставок по каждому лоту.

## 23. Критерии приемки

Система считается реализованной, если:
- парсер NickSell запускаются отдельно и собирают данные; 
- парсеры отправляют observation-сообщения в очередь;
- приемник читает сообщения и обрабатывает их идемпотентно;
- данные по доменам и торгам сохраняются в БД;
- финальная цена и финальный статус фиксируются для отследенных торгов;
- система корректно работает с IDN-доменами;
- сбой одного парсера не останавливает другие;
- ошибки и логи доступны для анализа;
- доступ к БД осуществляется только через сервисы и EF Core.
